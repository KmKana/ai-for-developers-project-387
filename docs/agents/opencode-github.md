# OpenCode в GitHub Actions

Правила для запусков OpenCode GitHub Action в этом репозитории (локальная копия действия по commit `77fc88c8ade8e5a620ebbe1197f3a572d29ae91a`). Они дополняют `AGENTS.md` и не заменяют описания навыков.

## Контекст Issue и Pull Request

Заголовок, тело, автор, дата, состояние и комментарии Issue/PR уже передаются в промпте. Для задач «объясни», «проанализируй», triage и подобных используйте этот контекст и файлы checkout.

Не проверяйте переменные окружения, не ищите токены и не вызывайте `gh` только для того, чтобы получить данные, которые уже есть в промпте. Если меток или другого поля нет в переданном контексте, явно отметьте это в ответе, но не переходите к поиску учётных данных.

## Файлы и секреты

Работайте с файлами внутри checkout. Не читайте `$HOME`, `~/.config`, `~/.gitconfig`, SSH-ключи и другие пути вне репозитория: `opencode.json` запрещает такой доступ, а в GitHub Actions некому ответить на интерактивный запрос разрешения.

Файлы `.env` и `.env.*` тоже запрещены к чтению. `.env.example` можно читать как безопасный пример. Ни в ответе, ни в комментариях не приводите значения ключей и токенов.

## GitHub CLI

`gh` не запрещён глобально. Используйте его только тогда, когда задача явно требует работы с GitHub Issues или Pull Requests и у текущего запуска есть необходимые разрешения — например, в сценариях `to-spec`, `to-tickets` и `implement-spec`.

В write-запуске (`opencode-write`) переменная `GH_TOKEN` задаётся из `github.token` этого job'а, у которого выставлено `permissions: issues: write`. Проверять токен или печатать его значение не нужно: `gh` берёт его из окружения автоматически.

Для обычного объяснения или анализа (`opencode-readonly`) `GH_TOKEN` не передаётся и права на Issues не выдаются; достаточно данных из промпта и репозитория. Дополнительные вызовы `gh` в таком случае являются лишней работой и всё равно не смогут изменить Issue.

## Режим доступа

CLI OpenCode `1.19.6` игнорирует вход `agent` экшна: сессия создаётся без явного агента, а сервер выбирает `default_agent` из конфигурации или `build` по умолчанию. Поэтому режим определяется конфигурацией, а не текстовой просьбой модели.

Для обычных комментариев (`explain`, triage, анализ требований) workflow запускает отдельный job `opencode-readonly` и передаёт `OPENCODE_CONFIG_CONTENT` из `opencode.readonly.json`. Этот inline-конфиг merging-ится последним и задаёт:

- `default_agent: readonly`;
- запрет `edit`, `bash`, `task`, `webfetch`, `websearch`, `todowrite`, `skill`, `lsp`, `question` и `external_directory`.

Агент `readonly` может читать файлы внутри checkout и пользоваться поиском, но не может редактировать файлы, выполнять shell-команды, запускать подзадачи или обращаться к сети. Это технический запрет на уровне разрешений, а не только инструкция в промпте. Поскольку грязного дерева не возникает, экшн не коммитит изменения, не пушит ветку и не открывает PR.

Для явных `to-spec`, `to-tickets` и `implement-spec` workflow запускает отдельный job `opencode-write`: inline-конфиг не передаётся, остаётся основной `opencode.json` с агентом `build` по умолчанию и полноценными инструментами, включая `bash`, `task` и GitHub CLI. Только в этом job'е задаются `permissions: issues: write` и `GH_TOKEN`. Упоминание навыка в запрете (`implement-spec не запускай`) write-режимом не считается: комментарии с отрицанием остаются read-only.

Workflow проверяет чистое рабочее дерево до запуска агента. После read-only запуска проверка повторяется; если файлы всё же изменились, job завершается ошибкой.

## Автоматический triage новых Issues

Отдельный workflow `.github/workflows/opencode-triage.yml` срабатывает только на `issues: [opened]` и только для Issues от `KmKana`, у которых автор не бот. Он повторно читает Issue через API (метки могут появиться после `opened`) и пропускает triage, если:

- Issue похоже на созданное навыками `to-spec`/`to-tickets` (в том числе по маркерам `Part of #N`, `## Что сделать`, `Спецификация:`);
- у Issue уже стоит одна из статусных меток из `docs/agents/triage-labels.md`: `ready-for-agent`, `ready-for-human` или `wontfix`.

Автоматический triage использует тот же закреплённый OpenCode Action, `OPENCODE_API_KEY`, OIDC-авторизацию и inline-конфиг `opencode.readonly.json`. `GH_TOKEN` не передаётся, `issues: write` не выдаётся: агент только анализирует Issue и код, а ответ публикуется инфраструктурой экшна как комментарий. Навыки `to-spec`, `to-tickets` и `implement-spec` в prompt'е явно запрещены, а параметр `skill` в readonly-конфиге технически заблокирован.

## Бюджет и независимое ревью PR

Интерактивные запуски `/oc` ограничены **тремя** вызовами модели на PR. Проверка выполняется в `opencode.yml` до вызова модели; счётчик хранится в истории запусков GitHub Actions (имя запуска содержит номер PR), поэтому повторные и отменённые попытки учитываются, а редактирование комментария бюджет не увеличивает. При исчерпании публикуется `budget_status: limit_exhausted` с SHA и ссылкой на логи.

Отдельный `opencode-review.yml` запускает независимого агента `reviewer` на событии `pull_request`, но пропускает недоверенные форки, draft и release-please PR; на один PR допускается не более **двух** автоматических вызовов модели, а повторный SHA не ревьюится. Ревьюер читает `REVIEW.md`, спецификацию #17, согласование #7, diff и результаты CI, не имеет `GH_TOKEN`, `bash`, `edit` и сети, а его отчёт публикуется как review от `github-actions[bot]`. Исправления по комментарию ревьюера автоматически не запускаются. PR, меняющий саму инфраструктуру ревью, получает `manual_review_required` и проверяется человеком.

Подробности, статусы, права и независимая браузерная проверка с Playwright-артефактом — в `docs/agents/review.md`. Шаблон PR — `.github/pull_request_template.md`.

## Версии

Workflow использует локальную копию действия из `.github/actions/opencode-pinned`, собранную по `anomalyco/opencode/github@77fc88c8ade8e5a620ebbe1197f3a572d29ae91a`. Установка OpenCode выполняется явно с `--version 1.19.6` и проверкой `opencode --version`; кэш по «последнему релизу» upstream-экшна не используется. Агент `build` ограничен 50 шагами (было 20), чтобы `to-spec` и `to-tickets` успевали опубликовать результат; read-only агент остаётся на 20 шагах. Таймаут каждого job'а — 15 минут.

## Модель и стоимость

Все запуски — `opencode.yml` (readonly и write) и `opencode-triage.yml` — используют `opencode/deepseek-v4.1-flash`, платную экономичную модель OpenCode Console. Официальный прайс на момент настройки (скидка 60%): `$0.12` за 1M входных токенов, `$0.48` за 1M выходных, `$0.0024` за 1M кэшированных чтений; без скидки — `$0.30` / `$1.20` за 1M. Скидка временная, перед изменением бюджета сверяйтесь с актуальным прайсом OpenCode Console.

Ключ берётся из секретов `OPENCODE_API_KEY` или `SECRETPAY` (используется первый заданный); он должен относиться к Workspace OpenCode Console с положительным балансом. Значения ключа не выводятся ни в логи, ни в комментарии. Если не задан ни один секрет, job завершается ошибкой до запуска модели, а не после таймаута на ошибке провайдера. Автоматическое пополнение баланса не включается, дорогие модели не выбираются: при исчерпании баланса запуск завершится ошибкой провайдера, а не переключится на более дорогую модель.

Смена модели не ослабляет ограничения: readonly/write-режимы, фильтры доверенных авторов и маркеров, `timeout-minutes: 15` и `concurrency` по номеру Issue/PR остаются прежними.

## Неинтерактивный режим

Запросы к пользователю (`question`) запрещены: если данных не хватает, включите уточняющие вопросы в итоговый ответ, но не ждите ответа в середине запуска.

Если инструмент заблокирован конфигурацией, продолжайте с доступной информацией и сообщите об ограничении в ответе. Не повторяйте заблокированный вызов и не пытайтесь обойти запрет через другие инструменты. Для задач «объясни/проанализируй» не меняйте файлы, не создавайте ветки, коммиты и Pull Requests, если это явно не требуется задачей.
