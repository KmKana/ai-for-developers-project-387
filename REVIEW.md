# Независимое ревью календаря

Этот документ задаёт критерии независимого ревью Pull Request в репозитории
`KmKana/ai-for-developers-project-387`. По нему работает автоматический ревьюер
`.github/workflows/opencode-review.yml` и человек, который проверяет PR вручную.
Ревью — совещательное: оно не меняет код и не запускает исправления.

## Источники истины

Ревьюер сверяет PR с документами в таком порядке:

1. [Согласование #7](https://github.com/KmKana/ai-for-developers-project-387/issues/7) —
   что именно подтвердил Владелец.
2. [Спецификация #17](https://github.com/KmKana/ai-for-developers-project-387/issues/17) —
   пользовательские истории, решения и критерии приёмки.
3. Тикеты #18–#21 — границы конкретного изменения и порядок зависимостей.
4. `AGENTS.md`, `README.md`, `GLOSSARY.md`, `docs/adr/` и `api/tsp/main.tsp` —
   правила проекта и контракт.
5. `REVIEW.md`, `.github/pull_request_template.md` и результаты CI этого PR.

Если PR противоречит согласованной спецификации, это блокирующее замечание, даже
если код «выглядит правильным». Если PR делает больше согласованного объёма, это
тоже замечание: сначала нужно отдельное согласование.

## Уровни замечаний

- **BLOCKER** — ошибка корректности, потеря данных, ослабление защиты от
  пересечений или конкурентности, нарушение контракта, утечка секрета либо
  публичных данных, сломанные обязательные тесты. Merge запрещён.
- **MAJOR** — требование спецификации не выполнено или выполнено частично,
  негативный сценарий не покрыт, риск отката или совместимости не описан.
  Нужно исправить до merge либо явно согласовать исключение.
- **MINOR** — поддерживаемость, читаемость, локальная неконсистентность,
  недостающая документация без влияния на поведение.
- **NIT** — вкусовщина и мелочи. Не блокирует merge.

Каждое замечание должно содержать `file:line`, суть, последствие и ссылку на
критерий из этого документа или на строку спецификации. Замечание без
доказательства — не замечание.

## 1. Защита от пересечений бронирований

Проверить, что после изменения выполняются все правила:

- Пересечение понимается как полуоткрытый интервал `[start, end)`: частичное
  наложение запрещено, стык разрешён (`start == existing.end` — валидная Запись).
- Конфликт проверяется по **всем** Записям Владельца, а не только по выбранному
  Типу встречи: календарь один на все типы.
- Проверка пересечения и добавление Записи остаются одной атомарной операцией
  `InMemoryStore.tryAddBooking` под монитором объекта. Нельзя выносить проверку
  в сервис, выполнять её до входа в монитор или заменять монитор на
  `ConcurrentHashMap` без доказанной атомарности.
- Любое пересечение возвращает HTTP `409` с кодом `SLOT_CONFLICT` и неизменным
  сообщением «Выбранное время уже занято. Выберите другой слот». Нельзя вводить
  отдельный код для «почти того же» времени.
- Новая тема разговора не должна влиять на проверку конфликта: Запись с темой и
  без неё конкурируют за один Слот одинаково.
- Порядок проверок календарных правил (окно, рабочие дни, часы, сетка) не должен
  меняться так, чтобы конфликт или календарная ошибка возвращались в другом
  приоритете без согласования.

Красный флаг: `synchronized` снят, проверка конфликта вызывается вне монитора,
`SLOT_CONFLICT` заменён на `VALIDATION_ERROR`, конфликт сравнивает только
`start` без `end` или игнорирует частичное наложение.

## 2. Конкурентные запросы

Проверить:

- `BookingConcurrencyTest` остаётся зелёным без ослабления: 12 и 32
  одновременных HTTP-запроса на один Слот дают ровно один `201`, остальные —
  `409 SLOT_CONFLICT`, а список Владельца содержит ровно одну Запись.
- Новые тесты с темой не заменяют старый тест и не уменьшают число потоков.
  Полезно добавить смешанный сценарий: часть запросов с темой, часть без.
- Нет гонки «проверить → подождать → добавить»; нет `Thread.sleep` внутри
  критической секции; нет общего изменяемого состояния вне монитора.
- Чтение (`upcomingBookings`, `listMeetingTypes`) возвращает неизменяемые
  снимки; итерация по внутреннему списку не выходит наружу.
- Гарантия остаётся в пределах одного процесса. Распределённые блокировки,
  внешние очереди и «оптимистичные» повторы не добавляются без отдельного
  решения и без теста на несколько инстансов.

Красный флаг: тест конкурентности удалён, помечен `@Disabled`, ослаблен до
«хотя бы один запрос успешен» или заменён unit-тестом без HTTP-шва.

## 3. Корректность доступных слотов

Проверить, что `GET /api/slots?meetingTypeId=…` и создание Записи используют
одни и те же правила:

- Часовой пояс Владельца — `Asia/Almaty`; рабочие дни — понедельник–пятница;
  рабочие часы — 09:00–18:00 по времени Владельца.
- Окно записи — 14 календарных дней, начиная с завтрашнего дня по времени
  Владельца (последний день включительно).
- Старт Слота — на 30-минутной сетке от 09:00, без секунд и наносекунд.
- Длительность Слота равна длительности выбранного Типа встречи (5–480 минут);
  конец встречи не выходит за 18:00.
- Занятые интервалы исключаются с учётом частичного наложения; стык разрешён.
- Слоты не должны «появляться» из-за смены темы, типа, порядка запросов или
  часового пояса клиента.
- Для неизвестного или пустого `meetingTypeId` контрактные ошибки
  (`VALIDATION_ERROR`, `MEETING_TYPE_NOT_FOUND`) остаются прежними.

Проверить границы: 17:30 для 30-минутного типа — валидно; 17:30 для
60-минутного — `OUTSIDE_WORKING_HOURS`; суббота и воскресенье — ошибка;
последний день окна включён; 15-й день — `OUT_OF_WINDOW`; старт с ненулевыми
секундами — `OFF_GRID`.

Красный флаг: изменение `BookingRules`, сетки, окна, рабочих часов или
длительности без согласования; разные правила в `SlotService` и
`BookingService`; фильтрация занятых Слотов только по точному старту.

## 4. Тема разговора до 300 символов

Сверить с #7 и #17. Обязательные свойства:

- `topic` необязателен. Запись без темы создаётся как раньше.
- Перед проверкой длины и сохранением строка обрезается по краям (`trim`).
  Пустая строка или строка только из пробелов — это отсутствие темы (`null`),
  а не ошибка.
- После trim длина **больше 300** символов отклоняется с HTTP `400`,
  кодом `VALIDATION_ERROR` и понятным сообщением «Тема разговора не длиннее
  300 символов». Ровно 300 символов принимается. Отдельный код ошибки не
  вводится.
- Длина считается одинаково на всех слоях. Если TypeSpec `@maxLength(300)`,
  Java `String.length()` и клиентский счётчик расходятся на emoji или
  суррогатных парах, это MAJOR: нужно зафиксировать единицу счёта (кодовые
  единицы UTF-16 либо кодовые точки Unicode) и покрыть её тестом. Молчаливое
  обрезание до 300 недопустимо.
- Тема хранится снимком на момент создания Записи. Редактирования, отмены и
  изменения темы после создания нет.
- В ответе без темы поля `topic` нет вообще (никакого `"topic": null`).
  Запись без темы сохраняет прежний набор из 8 полей; с темой добавляется
  девятое поле. Для этого нужен `@JsonInclude(NON_NULL)` или эквивалент.
- Значение в ответе уже нормализовано (`trim`).
- На Странице записи есть необязательное многострочное поле «Тема разговора» с
  подсказкой «Кратко опишите, что хотите обсудить» и предупреждением не
  указывать конфиденциальные данные. Клиентский лимит — только удобство,
  источник истины — бэкенд.
- На подтверждении Гостя и в списке Владельца тема показывается только если она
  непустая; пустых блоков и лишних строк для Записей без темы быть не должно.
- Тема не должна требоваться для отправки формы; ошибка 300/301 должна быть
  понятной и не терять введённый текст без необходимости.

Проверить негативные сценарии: 301 символ, 300 символов, пробелы вокруг текста,
только пробелы, пустая строка, переносы строк, кириллица, emoji, `<script>`
(React экранирует вывод; тема не должна вставляться через `dangerouslySetInnerHTML`),
очень длинная тема в запросе и отсутствие `topic` в JSON.

Красный флаг: тема обязательна; тема обрезается молча; `"topic": null` в ответе;
тема меняет правила Слотов или конфликтов; тема логируется вместе с email;
тема рендерится как HTML без экранирования.

## 5. Совместимость TypeSpec → OpenAPI → SDK → Spring Boot → React

Проверить всю цепочку, а не только конечный экран:

- Изменение начинается в `api/tsp/main.tsp`: у `Booking` и `BookingInput` есть
  необязательное `topic?: string` с `@maxLength(300)` и понятным описанием.
- `api/openapi/openapi.yaml` и `frontend/src/sdk` перегенерированы командами
  `npm run generate` и `npm run generate-sdk`, а не отредактированы руками.
  `mise run check-contract` подтверждает отсутствие расхождений.
- Spring Boot DTO, сервис, хранилище и сериализация соответствуют контракту:
  имена полей, необязательность, коды ошибок и сообщения не расходятся.
- React использует только сгенерированный SDK: нет прямых `fetch`/`axios` к
  `/api`, нет вручную продублированных URL и типов ответа.
- Контрактные тесты (`OpenApiConformanceTest` и смежные) обновлены и проверяют
  ответ с темой, ответ без темы и ошибку валидации.
- Обратная совместимость: старый клиент без `topic` продолжает работать;
  отсутствие поля не ломает существующие тесты на 8 полей.

Красный флаг: правка сгенерированных файлов; `topic` есть в SDK, но не в
TypeSpec; расхождение имени (`topic` vs `comment`/`subject`); новая цепочка
контракта параллельно со старой; прямые запросы из компонентов.

## 6. Регрессионные и негативные сценарии

Обязательный минимум для PR с темой разговора:

- Создание Записи с темой и без темы; тема возвращается в ответе создания и в
  списке Владельца.
- `trim` и пустая/пробельная тема; ровно 300 и 301 символ; сообщение и код
  ошибки.
- Конфликт Слота и частичное наложение разных Типов встреч; неизменное
  сообщение `SLOT_CONFLICT`.
- Одновременные запросы (существующие 12/32 и, желательно, смешанные
  с темой/без темы).
- Календарные ошибки: `OFF_GRID`, `OUTSIDE_WORKING_HOURS`, `OUT_OF_WINDOW`,
  неизвестный Тип встречи, пустой `meetingTypeId`.
- Отображение темы у Гостя и Владельца; отсутствие пустого блока без темы.
- Существующие тесты каталога, создания Типа встречи, списка Владельца и
  контракта остаются зелёными; ни один тест не удалён и не ослаблен.
- Новые тесты проверяют внешнее поведение через HTTP-шов или публичный рендер
  React, а не приватные детали реализации.

Проверить, что PR не добавляет «зелёные» тесты, которые проходят при сломанном
поведении: например, принимают и `200`, и `409`, не проверяют тело ошибки или
пропускают проверку конкурентности.

## 7. Ограничения публичного доступа к данным

Проект намеренно без авторизации: `GET /api/bookings` доступен любому, кто знает
адрес, и тема разговора **не является приватной**. Это осознанное ограничение
учебной версии, а не обещание приватности.

Проверить:

- PR не расширяет публичный доступ: нет новых эндпоинтов, отдающих все Записи,
  email, темы или историю; нет темы в каталоге Типов встреч и в слотах.
- В `README.md` и описании контракта есть предупреждение, что тема и данные
  Гостя не приватны, и рекомендация не указывать конфиденциальные данные.
- В интерфейсе есть предупреждение рядом с полем темы.
- Тема, имя и email не пишутся в логи, метрики, аналитику, URL или сообщения об
  ошибках. Не добавлять `System.out.println`, `console.log` с PII, `toString()`
  Записи в логи и трассировки.
- Ошибки не раскрывают внутренние идентификаторы, стектрейсы и чужие данные.
- CORS, заголовки и прокси не расширяются без согласования; секреты не попадают
  в клиентский бандл.
- Не появляется ложного ощущения авторизации: если PR добавляет «личный
  кабинет», токены или ограничение доступа, это отдельная задача, а не
  побочный эффект темы разговора.

Красный флаг: новый публичный эндпоинт с ПДн; тема в URL; email/тема в логах;
`dangerouslySetInnerHTML`; попытка «скрыть» данные только в UI; секрет в
репозитории или в артефакте.

## 8. Тесты, CI и доказательства

PR должен содержать:

- точный head SHA, для которого получены результаты;
- ссылку на запуск `check` и его статус;
- ссылку на запуск `browser-check` (независимый Playwright) и артефакт с trace
  или скриншотами;
- вывод `mise run check` (или ссылку на него), включая `BookingConcurrencyTest`,
  `OpenApiConformanceTest`, Vitest и сборку;
- `actionlint` для изменённых workflow и `git diff --check`;
- перечень проверенных вручную негативных сценариев, если автоматики нет.

Не считать доказательством:

- зелёный CI на другом SHA;
- «тесты проходят локально» без ссылки/вывода;
- скриншот без trace и без указания SHA;
- тест, который пропускает проверку при отсутствии окружения;
- артефакт браузерной проверки, собранный не из точного head SHA PR.

Браузерная проверка обязана проверить `git rev-parse HEAD` против
`github.event.pull_request.head.sha` и сохранить Playwright trace или
скриншоты как артефакт. Если проверка упала, артефакт всё равно должен быть
доступен.

## 9. Риск и откат

PR должен явно описать:

- **Door:** one-way (данные/контракт нельзя откатить без потерь) или two-way
  (откат безопасен).
- **Blast Radius:** какие модули, контракты, пользователи и окружения
  затронуты; затронут ли публичный деплой.
- **Данные:** данные в памяти, миграций нет; перезапуск сбрасывает состояние.
  Если PR добавляет внешнее хранилище — это отдельное согласование.
- **Совместимость:** старые клиенты, закешированные SDK, контрактные тесты.
- **Откат:** revert коммита/PR, регенерация контракта, отсутствие миграций,
  проверка, что после отката `mise run check` и браузерный E2E зелёные.
- **Наблюдаемость:** как понять, что после merge стало хуже, и что смотреть.

Красный флаг: «откат не нужен», «риска нет», ручные шаги без команд, откат,
который требует удалить данные или секреты.

## Формат отчёта ревьюера

Автоматический ревьюер публикует один комментарий к PR со следующими разделами:

```markdown
> *This review was generated by AI. It does not modify code.*

## Итог
APPROVE | COMMENT | REQUEST_CHANGES — одно предложение почему.

## Блокирующие замечания
- `path:line` — что не так, почему это BLOCKER, как проверить.
  Критерий: REVIEW.md §…

## Некритичные замечания
- …

## Пробелы в тестах и доказательствах
- …

## Трассировка к спецификации #17
- US/критерий — выполнен / частично / не выполнен, где доказательство.

## Риск и откат
- …

## Что проверено
- diff, REVIEW.md, #7, #17, CI, браузерный артефакт; что было недоступно.
```

Если блокирующих замечаний нет, явно написать «Блокирующих замечаний нет».
Ревьюер не предлагает готовых патчей и не запускает исправления: только
замечания и следующий шаг для человека.

## Что не входит в ревью

- Реализация тикетов #18–#21 и любые продуктовые изменения: это отдельный PR.
- Автоматическое исправление кода по комментарию ревьюера.
- Изменение секретов, моделей, бюджета и workflow без отдельного согласования.
- Требование авторизации, приватности `GET /api/bookings`, внешних календарей
  и уведомлений: они вне согласованного объёма #7/#17.
